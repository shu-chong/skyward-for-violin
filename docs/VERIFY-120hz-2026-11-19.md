## 3. 带宽账

一帧 3200×2136×4 B = 27,340,800 B（26.07 MiB）。
120 Hz 扫描读出 3.28 GB/s；若同时整帧写回，再 3.28 GB/s，合计约 6.6 GB/s。
144 Hz 时是 3.94 + 3.94 ≈ 7.9 GB/s。
这两个数字相对 8.53 GHz 的内存控制器都不算高，所以 144 Hz 那次 903 次 underflow 更像是**调频延迟/投票缺失**而不是纯带宽不足：DPU 不投票 → DDR 常驻 836 MHz → 每帧取像素都要等，抖动累积成下溢。把下限钉死，等于消掉了这个等待。这也解释了为什么 90 Hz "本来就没事"：2.46 GB/s 在最低档也勉强够。

## 4. 局限（没有覆盖到的）

1. **首次 modeset 没抓到**。环形缓冲从 `110.8 s` 才开始，而面板是开机后约 20 s 点亮的，`[DPU-I] ... new refresh rate is 120(hz)` 那条已经滚掉。上面的结论靠 DRM 原子状态定案，不靠那条日志。
2. **拿不到渲染耗时**。`crates/skyward/src/ui.rs:1870` 有 `eprintln!("frame {:?} in {} ms", ...)`，但这版 recovery 的 stdio 没有接进 kmsg，`dmesg` 里 0 条。所以「面板 120 Hz」是硬证据，「页面滑动更顺」还需要人眼确认——如果软件光栅一帧就要 12 ms，120 Hz 只是白给功耗。
3. **静态画面 ≠ 动画压力**。静止时 DPU 仍以 120 Hz 读 framebuffer（3.28 GB/s 照跑），但动画会多出整帧写回，峰值更高。要压满负载得滑动翻页时再抓一次。

## 5. 下一步
